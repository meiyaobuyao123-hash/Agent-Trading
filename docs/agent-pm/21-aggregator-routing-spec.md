# §0 总览 — 这事在干什么

## 0.1 一句话定位

**给 AI Agent 配一套"任何币都能买、买就买到最好价、不挨夹、不踩雷、跨链无感"的底层交易能力**。

## 0.2 用户痛点(为什么必须自建,不能只用 Jupiter/1inch)

| 痛点 | 用户表达 | 当前竞品(Jupiter/1inch/OKX)缺什么 |
|---|---|---|
| 跨链买币要切 5 个 App | "我想从 USDC 直接买 SOL 上的某个新币,中间要去币安提到 ETH、过桥、再换 SOL、再 swap,半小时" | 单链聚合器,跨链不管 |
| 不懂滑点设几 | "0.5% 还是 1% 还是 5%?设小了交易失败,设大了被砸盘" | 让用户自填,没"按场景智能推荐" |
| 被夹经常发生 | "买完看链上记录,有 sandwich 在我前后各一笔,亏 3-5%" | 1inch 有 Fusion 但用户不知道开,Jupiter 默认不防夹 |
| 不知道地址该不该信 | "看到 KOL 喊单 token,买完发现是蜜罐,卖不出去" | 聚合器不做蜜罐检测 |
| 跟单太慢 | "看到鲸鱼买入,等我手动操作过去,价格已经涨 30%" | 聚合器不连数据源,手工监控 |
| 想"AI 帮我做"但又怕 | "全自动我不放心,纯手工又懒,想要 AI 给建议+我点确认" | 全聚合器都是纯工具,没决策辅助 |

## 0.3 产品定位的 3 个差异化

1. **跨链原生**:用户视角"我有 USDC,我要买 X 币(无论哪条链)" — 中间过程对用户透明,产品自己决定走哪条桥/路由
2. **AI 决策辅助**:不只是"找最便宜路径",还要"判断这笔值不值得现在做"(信号强度 + 风控分 + 时间窗)
3. **风险前置拦截**:用户提交意图前,系统已经过 5 道风控筛(黑名单 / 蜜罐 / 高税 / 低流动性 / 大额跟单密集)

# §1 聚合交易 (Aggregator)

> 一句话:**用户给 token 地址 + 金额 + 方向,我们出"最优价格 + 滑点估算 + 交易时长预估" 3 个数,用户点一下完成**。

## 1.1 用户故事(3 个最重要)

### US1.1 — 新手买 meme 币
> "我看到推特有人喊 SOL 上一个 meme 币 $X,我有 $100 USDC 在 Solana 钱包,我想花 $50 买这个币。希望 1 秒内告诉我最终能拿到多少币、滑点多少、要不要 1 秒内确定。"

**核心需求**:速度 + 价格透明 + 不让用户自己设滑点。

### US1.2 — Pro 用户跨 DEX 比价
> "我要买 $5000 的 ETH,我想看 Uniswap V3 / Sushi / 1inch / Curve 各家报价,选最便宜的。"

**核心需求**:可选"展开看明细"模式 + 历史价格对照 + 手动选路由。

### US1.3 — 跟单大单
> "Agent 检测到鲸鱼刚买了 X 币,提示我跟单。我点'跟单 $200',希望系统自动选最优路由 + 不被夹 + 1 分钟内确认链上。"

**核心需求**:防夹 + 速度 + 失败回退到下个备选。

## 1.2 产品边界

### 我们做
- ✅ 聚合 5 个以上 DEX 的报价
- ✅ 自动选最优(默认)
- ✅ 用户可选"展开手动选"
- ✅ 滑点智能推荐(按 token 流动性、波动率、历史)
- ✅ 报价失败时自动降级到次优
- ✅ 报价缓存(高峰期 100+ 用户同时查同一币不要打爆数据源)

### 我们不做
- ❌ 限价单(MVP 不支持,V2 才考虑)
- ❌ 永续 / 期权
- ❌ 自定义 RPC endpoint(用户改 RPC 风险高)
- ❌ 隐私交易(法律灰区,先不碰)

## 1.3 Solana 端聚合 — 接哪些 DEX

### 1.3.1 必接(MVP 上线)

| DEX | 聚合方式 | 为什么 |
|---|---|---|
| **Jupiter** | 直接调 Jupiter Aggregator API | Solana 上 90%+ DEX 流动性的事实标准 |
| **Raydium** | 通过 Jupiter 间接 | Raydium 是最大 AMM,Jupiter 已聚合 |
| **Orca** | 通过 Jupiter 间接 | 第二大 AMM,Jupiter 已聚合 |
| **Pump.fun (Bonding Curve)** | 直连 pump 合约 | meme 币早期阶段在 pump.fun,Jupiter 不一定聚合 |

**产品决策**:**MVP 期只接 Jupiter + Pump.fun 直连**。Jupiter 一家覆盖 90%,Pump.fun 是补 meme 币早期场景的关键。

### 1.3.2 V1 加(R50)

| DEX | 用途 |
|---|---|
| **Raydium 直连** | 当 Jupiter 报价比单跳 Raydium 还差时(rare,但存在),自己出报价做 fallback |
| **Meteora** | 集中流动性,某些 token 滑点比 Jupiter 好 |

### 1.3.3 不接(明确不接,免得团队来回讨论)

- **Serum / OpenBook** — 订单簿模式,流动性不够,Jupiter 已经覆盖
- **Aldrin / Saber** — TVL 太低,Jupiter 已经聚合

### 1.5.2 Pro 模式(展开后)

## 1.6 滑点智能推荐(产品级核心)

**痛点**:用户不知道该填几。

### 1.6.1 推荐规则(产品决策树)

```
1. 主流币(SOL/ETH/BTC/USDC/USDT)→ 默认 0.5%
2. 流动性 > $1M token → 默认 1%
3. 流动性 $100k-$1M token → 默认 2%
4. 流动性 $10k-$100k token → 默认 3% + UI 加黄色"流动性偏低"提示
5. 流动性 < $10k token → 默认 5% + UI 红色"流动性极低,可能交易失败"提示
6. CRISIS regime(BTC 24h < -10%)→ 当前推荐值 × 1.5
7. token 24h 波动 > 50% → 推荐值 × 1.3
```

### 1.6.2 用户可改

界面"滑点 0.8%"可点击,弹出滑动条 0.1% — 50%。**默认 + 推荐值是产品价值,但永远尊重用户选择**。

### 1.6.3 滑点失败兜底

如果设的滑点交易失败(price impact 超阈值):
- 系统自动重试 1 次,滑点提到 1.5x
- 仍失败 → 弹窗"价格波动过大,请稍后再试" + 显示当前实时价

## 1.7 报价缓存策略

**痛点**:50 个用户同时看同一个 token,打爆 API。

### 1.7.1 缓存规则

| 数据 | 缓存时长 | 失效条件 |
|---|---|---|
| 主流币基础报价 | 5 秒 | TTL |
| Meme 币报价 | 2 秒 | TTL(波动大) |
| 用户准备下单的具体报价 | 不缓存 | 必须实时 |
| token 元数据(name/symbol/decimals) | 24 小时 | 用户主动刷新 |
| 流动性深度 | 60 秒 | TTL |

### 1.7.2 用户视角

如果显示了缓存价,**UI 必须标注"3 秒前更新"**,点击交易前自动刷新一次实时价。

## 1.8 报价失败降级

按这个顺序降级:

```
1. 主聚合器(Jupiter/1inch)失败
   → 2. 备用聚合器(0x/Pump 直连)
       → 3. 单 DEX 直连(Uniswap/Raydium)
           → 4. 显示"暂时无法成交,稍后再试"+ 给客服 / 手动操作引导
```

每一步降级都**埋点**,运营能看到"今天 Jupiter 几次失败、走了几次 fallback"。

## 1.9 验收标准(给 QA + PM 验收)

| 标准 | 通过条件 |
|---|---|
| **报价速度** | P95 < 800ms,P99 < 1.5s |
| **报价准确性** | 报价与实际成交价偏差 ≤ 滑点设定值 99% |
| **降级率** | < 2%(98% 以上不需要走 fallback) |
| **失败率** | 用户提交后真实成交失败率 < 5% |
| **滑点推荐准确率** | 推荐值导致失败率 < 3% |
| **缓存命中率** | 高峰期 ≥ 70%(减负压) |

# §2 智能路由 (Smart Routing)

> 一句话:**用户给我个交易意图,我决定"经过哪些 DEX、拆几单、用什么 RPC 防夹、什么时间窗发"** — 用户感知不到这层,但是产品最大差异化。

## 2.1 用户故事

### US2.1 — 大单不被砸盘
> "我要买 $5000 的中盘币,直接一笔走会让价格瞬间冲高 5%,我损失 $250。希望系统自动拆 5 笔分钟级发,平均价更好。"

### US2.2 — 跨 DEX 路由
> "USDC → X 币没有直接池,要走 USDC → SOL → X 币两跳。系统自动找最优中间币和路径。"

### US2.3 — MEV 防夹
> "我注意到 ETH 上经常被夹,买完看链上历史前后各有一笔机器人。希望系统自动用 Flashbots 隐藏待发交易。"

## 2.2 单跳 vs 多跳

### 2.2.1 决策

| 场景 | 默认行为 |
|---|---|
| 直接池存在(USDC/SOL)| 单跳 |
| 直接池存在但流动性 < 想买金额 × 5 | 多跳(避免吃光池子) |
| 没有直接池 | 多跳(必走) |
| 用户 Pro 模式选指定路径 | 按用户选 |

### 2.2.2 中间币选择优先级

```
USDC > SOL/ETH/BNB(链原生)> WBTC > USDT > 其他
```

例:USDC → 某 meme 币 在 Solana 上,中间币优先 SOL(因为流动性最深)。

## 2.3 拆单 (Split Routing)

### 2.3.1 触发拆单的条件(任一)

```
1. 单笔成交后预估价格冲击 > 2%
2. 单笔金额 > 该 token 24h 交易量的 10%
3. 单笔 > $5000(无论 token)
4. 用户主动选"拆单优化"
```

### 2.3.2 拆单策略

| 用户选项 | 行为 |
|---|---|
| **快速**(默认)| 1 笔搞定,接受滑点 |
| **优化**(用户主动)| 拆 3-5 笔,5-30 秒间隔,平均价更好但慢 |
| **隐蔽**(V2)| 拆 10+ 笔,随机间隔,反夹 + 反 sandwich |

### 2.3.3 拆单失败处理

- 第 1-3 笔成功,第 4 笔失败 → 不回滚已成交,告诉用户"已完成 60%,剩余因 X 失败可手动续"
- 全失败 → 明确告诉用户"未成交"

## 2.4 滑点控制(运行时,不是 §1.6 配置时)

### 2.4.1 三档防御

```
1. 提交前预估:报价时算 price impact + 滑点设定 = 用户接受最大损失
2. 提交时锁定:链上交易带 minOutAmount(用户接受的最小到手量)
3. 链上保护:DEX 智能合约自己检查,实际滑点 > minOut → 交易回滚
```

### 2.4.2 滑点动态调整

如果**首次提交时滑点设 0.8% 失败**,自动重试逻辑:

```
重试 1:滑点 × 1.5(0.8% → 1.2%)
重试 2:滑点 × 2(0.8% → 1.6%),且更新报价
重试 3:放弃,告诉用户"价格波动过大"
```

每一次重试用户都看到"正在重试,价格波动较大..."loading 提示。

## 2.5 MEV 防夹

### 2.5.1 各链方案

| 链 | 防夹方法 | 用户视角 |
|---|---|---|
| **Solana** | 通过 Jupiter 自动 + 加优先费(priority fee)| 默认开,无感 |
| **ETH 主网** | Flashbots Protect RPC 私有内存池 | 默认开,P95 + 5 秒延迟换免夹 |
| **BSC** | bloXroute Protect | 默认开 |
| **Base** | 不需要(L2 mempool 隐私) | 自然防夹 |
| **Arb** | 不需要(L2)| 自然防夹 |

### 2.5.2 用户控制

界面"高级选项"允许用户:
- 关闭 MEV 防护(选了"快速,接受夹")
- 加大优先费(快速通道,Solana 场景)
- 选 specific RPC(Pro 用户)

**默认全开,普通用户无感**。

### 2.5.3 防夹效果度量

每周后台报告:
- 实际被夹笔数 vs 总笔数
- 防夹收益(估算"如果不开 vs 开了"的滑点差)

## 2.6 重试与失败处理

### 2.6.1 失败分类

| 失败类型 | 用户感知 | 系统行为 |
|---|---|---|
| RPC 超时 | "网络拥堵,正在重试" | 自动换 RPC 重试 3 次 |
| 滑点过高 | "价格波动较大" | 自动放大滑点重试 |
| nonce 冲突(EVM)| 无感 | 重新拿 nonce 重发 |
| gas 不足 | "估算 gas 不够,正在调整" | 自动加 gas 重发 |
| token 余额不足 | "余额不足" | 不重试,UI 拒绝 |
| 蜜罐拒卖 | "此 token 无法卖出,可能为蜜罐" | 标记 + 加黑名单 |
| 链拥堵 | "链上拥堵,5 分钟后再试" | 不重试,排队 |

### 2.6.2 重试上限

每笔交易最多 3 次重试,每次间隔 2-5 秒。**3 次都失败,告诉用户原因 + 建议**(不要无限重试烧 gas)。

## 2.7 Gas / 优先费策略

### 2.7.1 默认策略

| 链 | 默认 |
|---|---|
| Solana | priority_fee = 当前网络中位数 × 1.2 |
| EVM | EIP-1559:maxFee = 基础 × 1.5,priorityFee = 中位数 × 1.2 |

### 2.7.2 紧急加速

如果交易 60 秒未上链,自动 bump:
- Solana:重发新交易,优先费 × 2
- EVM:用同 nonce + gas × 1.5 替换原交易

加速最多 2 次,仍卡住 → 用户感知"链上拥堵,可手动取消"。

## 2.8 验收标准

| 标准 | 通过条件 |
|---|---|
| 多跳路径成功率 | ≥ 95% |
| 拆单总成本 vs 单笔 | 大单(>$5000)拆单后实际成交均价比单笔好 ≥ 0.5% |
| MEV 防夹有效率 | ETH/BSC 实际被夹笔数 < 1%(开启防护时) |
| 失败重试成功率 | 重试 3 次内成功 ≥ 80% |
| Gas 预估准确率 | 预估 gas 与实际偏差 < 30% |

# §3 钱包基础功能

> 一句话:**用户能创建、导入、转账、签名,完全不懂"私钥/助记词"也能用得起来,但 Pro 用户能完全掌控**。

## 3.1 用户故事

### US3.1 — 小白创建第一个钱包
> "我刚下载 App,从来没用过 web3 钱包。希望 App 帮我自动创建一个,告诉我'已建好,你的地址是 0x...,请抄写这 12 个备份词放安全的地方'。我点抄写完了就能用。"

### US3.2 — Pro 用户导入主钱包
> "我有 Phantom / MetaMask 主钱包,我想导入到 App 里用 Agent 自动交易,但希望 App 不真存私钥,每次交易我自己点 Phantom 确认。"

### US3.3 — 紧急转账
> "我看到鲸鱼买入信号,我钱包里 Solana 没钱,但 ETH 上有 $500。希望我能在 App 里一键 '从 ETH 转 $200 到 SOL'(走桥),5 分钟内到账买入。"

### US3.4 — 多钱包管理
> "我想分 3 个钱包:测试钱包($50)、跟单钱包($500)、长期持仓钱包($5000)。每个钱包独立余额、独立策略。"

## 3.2 创建钱包(App 内生成)

### 3.2.1 流程

```
1. 用户点"创建钱包"
2. App 在本地生成 12 个助记词 + 派生地址
3. 强制让用户做 1 次 "抄写 → 验证"(随机抽 3 个词让用户回填)
4. 验证通过 → 钱包激活,主页显示
5. 私钥本地加密存(iOS Keychain / Android Keystore)
6. 默认创建多链地址:Solana + ETH(同一助记词派生)
```

### 3.2.2 备份提示

- 创建后立刻 modal 弹"现在去抄助记词?"(强引导)
- 主页持续 banner "未备份的钱包"提示,直到用户点"我已备份"
- 大额交易($1000+)前,如果未备份再 modal 拦一次

### 3.2.3 不做的事

- ❌ App 帮用户存助记词到云(违背 self-custody 原则)
- ❌ 钱包恢复功能(用户丢了助记词,产品方无法救)

## 3.3 导入钱包

### 3.3.1 三种导入方式

| 方式 | 适用人群 | 安全等级 |
|---|---|---|
| **助记词导入** | 已有钱包用户 | 高(用户输入,本地加密)|
| **私钥导入** | Pro 用户(知道风险)| 高(同上)|
| **WalletConnect 连接** | 不愿交私钥的用户 | 最高(私钥永远在用户原 App)|

### 3.3.2 助记词 / 私钥导入流程

```
1. 用户输入(粘贴板自动识别格式)
2. 本地校验合法性(checksum / 长度)
3. 派生地址 → 显示"这个地址你确认吗?"
4. 用户确认 → 加密存本地 + 加密上传后端(为了 Agent 自动交易)
5. 后端只存加密后的密文,主密钥分开存
```

### 3.3.3 WalletConnect 模式

```
1. 用户扫 App 显示的 QR 或点击链接
2. 跳到 Phantom / MetaMask 授权
3. App 拿到地址,但拿不到私钥
4. 每次交易必须用户在原钱包 App 点确认 → 不适合"全自动 Agent",
   但适合"AI 给建议 + 我点确认" 模式
```

**产品决策**:WalletConnect 在 V1 提供,但 UI 上明确说"此模式下 Agent 不能自动交易,只能给你下单建议"。

## 3.4 多钱包管理

### 3.4.1 默认 1 钱包,可加多钱包

```
[ 主钱包 - 0x6F...3a ]   ← 默认
   余额:$1,250
   策略:跟单 SOL 头部

[ + 添加钱包 ]
```

点"添加钱包" → 弹"创建新钱包 / 导入助记词 / 导入私钥 / 连接 WalletConnect" 4 选 1。

### 3.4.2 钱包切换

主界面右上角"当前钱包"hamburger,点击展开列表,1 步切换。

### 3.4.3 每钱包独立

- 余额独立显示
- 策略独立绑定
- 交易历史独立
- 资金不会自动跨钱包流转(避免误操作)

### 3.4.4 上限

每用户最多 5 个钱包(避免无限创建混乱)。

## 3.5 转账(钱包间 / 给外部地址)

### 3.5.1 转账场景

| 场景 | 流程 |
|---|---|
| App 内钱包间转 | 用户选源 + 目标 + 金额,系统按链处理(同链直转 / 跨链走桥) |
| 转给外部地址 | 用户输入地址 + 金额,系统识别链 + 蜜罐黑名单检查 |
| 转给 ENS / SNS 域名 | 系统自动解析,显示真实地址给用户确认 |

### 3.5.2 转账确认页

转账前 100% 必须有确认页:

```
你要转:
  从:主钱包(0x6F...3a)
  到:0xAB...12  ← 全地址,方便核对
        OR  vitalik.eth  ← 如果是 ENS
  金额:100 USDC
  网络:Ethereum
  Gas:$2.50
  ────────────────
  总扣:100 USDC + $2.50 gas
  
  ⚠️ 请仔细核对地址,转出无法撤回
  
  [ 取消 ]    [ 确认转账 ]
```

### 3.5.3 大额二次确认

转账金额 > $1000 时,确认页加一道 "再次输入金额最后 3 位数字":

```
你输入了金额 $5,432
请输入金额最后 3 位:[ ___ ]
```

防误转。

## 3.6 签名交互

### 3.6.1 三种签名场景

| 场景 | 用户感知 |
|---|---|
| Agent 自动交易(私钥本地加密)| 无感,自动签 |
| Agent 自动交易(WalletConnect)| 弹原生钱包确认 |
| 用户主动转账 | 确认页 → 点确认就签了 |

### 3.6.2 签名安全 + 防钓鱼

- 签名内容可读化(不显示 raw bytes,显示"批准 100 USDC swap to X 币")
- 不签陌生合约的 approve 无限额度,默认建议改成"准确金额 + 1.1x"

## 3.7 安全 + 备份

### 3.7.1 必做

- 私钥本地加密(iOS Keychain / Android Keystore)
- 后端存的密文(用主密钥再加一层),即使 DB 泄漏单独不能解
- 所有 API 请求 HTTPS + JWT 鉴权
- 大额交易 + 加密钱包导入需要 App 内密码或生物识别

### 3.7.2 用户教育

- 创建后强制提示备份
- 主页常驻"安全检查清单"(已备份 / 已开生物识别 / 已设密码)
- 大额前最后一道询问

## 3.8 验收标准

| 标准 | 通过条件 |
|---|---|
| 创建钱包 | < 30 秒完成 |
| 导入钱包(助记词)| < 15 秒完成 |
| 转账成功率 | ≥ 99%(排除用户输错地址) |
| 误转防御 | $1000+ 二次确认必触发 |
| 私钥泄漏率 | 0(任何 log / 错误信息不能含私钥) |
| 多钱包切换 | < 1 秒 |

# §4 跨链资金流转

> 一句话:**用户视角"我有 USDC,我要买另一条链上的 X 币" — 中间过桥过程对用户透明,产品自己选最优桥**。

## 4.1 用户故事

### US4.1 — 跨链购买
> "我钱包里有 $500 USDC 在 Solana,我看到 Base 上一个 token 想买 $200。希望 App 一键完成 Solana USDC → Base USDC → Base X 币,5 分钟内到账。"

### US4.2 — 跨链转账
> "我要把 ETH 上的 $1000 USDC 转到 BSC 的另一个钱包。希望 App 自动选最便宜最快的桥。"

### US4.3 — 跨链 Agent 自动跟单
> "Agent 检测到 BSC 上鲸鱼买入,但我钱包都在 Solana。希望 Agent 自动跨链 + 跟单,我提前授权'最多用 $300'。"

## 4.2 桥选型(我们接哪些)

### 4.2.1 三家桥并行,做聚合

| 桥 | 优势 | 劣势 |
|---|---|---|
| **Wormhole** | Solana ↔ EVM 最稳;TVL 大 | 速度中等(2-15 分钟) |
| **deBridge / DLN** | 速度快(30 秒-2 分钟);链多 | 滑点稍大 |
| **Axelar** | 多链(15+);开发者友好 | 用户量小 |
| **Across** | EVM 之间最快(< 1 分钟)| 不支持 Solana |

### 4.2.2 默认策略

```
跨链 = Solana ↔ EVM        → Wormhole(主)+ deBridge(fallback)
跨链 = EVM ↔ EVM(主流)    → Across(主)+ deBridge(fallback)
跨链 = EVM ↔ EVM(小众)    → Axelar(主)+ deBridge(fallback)
```

### 4.2.3 何时不接桥(MVP)

- ❌ Stargate / Hop / Bungee — 当前需求覆盖不到,先不接
- ❌ Layer Zero 直连 — 通过上述桥间接用

## 4.3 跨链报价聚合

### 4.3.1 用户视角看到什么

```
你要:Solana USDC $200 → Base 上 X 币

最优路径:
  Solana USDC ─[Wormhole]─→ Base USDC ─[Aerodrome]─→ X 币
  
  预计到账:198.50 X 币
  桥费 + DEX 费:$0.85
  预计时长:3 分钟
  
  > 展开看其他桥
  
  [ 一键跨链购买 ]
```

### 4.3.2 桥对比(Pro 模式)

| 桥 | 到账量 | 总费 | 时长 |
|---|---|---|---|
| Wormhole + Aerodrome | 198.50 | $0.85 | 3 min |
| deBridge + Aerodrome | 198.20 | $1.10 | 1.5 min ⚡ |
| Axelar + Uniswap | 197.80 | $1.40 | 5 min |

用户可手动选(默认按"到账最多"排序)。

## 4.4 跨链进度跟踪

### 4.4.1 状态机(用户看到)

```
已发起 → 源链确认中(等 12 个区块)→ 桥处理中 → 目标链广播 → 目标链确认中 → 已到账

⏳ 当前:桥处理中(约 1 分 30 秒,预计 2 分钟后完成)
```

### 4.4.2 通知

- 进度 25% / 50% / 75% / 100% 各推送一次
- 异常(失败 / 卡住超 10 分钟)立即推送

### 4.4.3 进度页可分享

如果用户切到别的 App,进度仍后台跑,完成后系统通知。

## 4.5 跨链失败回滚

### 4.5.1 失败场景

| 场景 | 处理 |
|---|---|
| 源链发起后桥未处理(< 5 分钟)| 等,桥可能慢 |
| 桥确认了但目标链广播失败 | 资金锁桥里,联系桥 SDK 提取 |
| 桥滑点超阈值,自动回退 | 桥支持的话自动回 USDC,不支持告诉用户 |
| 目标 token swap 失败(收到 USDC 但买不到 X 币)| 资金以 USDC 形式留在目标链钱包,通知用户 |

### 4.5.2 用户视角承诺

明确告诉用户:**"如果跨链中途失败,你的资金不会消失,可能停在中间链上 USDC 形式。我们会通知你下一步怎么办。"**

绝不让用户感觉钱蒸发。

## 4.6 桥黑名单 + 风险拦截

### 4.6.1 桥黑名单源

- 监测桥本身被攻击 / 暂停的官方公告
- 一旦某桥被列入黑名单,**立即从可用列表剔除**,直到复活

### 4.6.2 黑名单生效

- 后端实时维护
- 前端拉到列表后从用户可选项里移除
- 全局通知"X 桥暂时不可用"

### 4.6.3 历史攻击案例(产品参考)

- 2022 Wormhole 被盗 $325M(已修)
- 2022 Nomad 被盗 $190M(已停)
- 2023 Multichain 跑路(全资金锁)

**产品决策**:**桥的安全性是动态的**,我们建立"桥健康度"内部分数,持续监控。低于阈值自动黑名单。

## 4.7 验收标准

| 标准 | 通过条件 |
|---|---|
| 跨链成功率 | ≥ 95% |
| 平均到账时长 | < 5 分钟(主流路径) |
| 用户感知到的失败 | < 2%(中途状态被告知,不蒸发) |
| 桥费用比单一桥 | 平均省 ≥ 5%(因为聚合) |
| 黑名单生效时长 | < 1 小时(从公告到剔除)|

# §6 风控阻断

> 一句话:**用户在花钱前,产品已经过 5 道筛把明显雷的拦在前面**。

## 6.1 用户故事

### US6.1 — 蜜罐拦截
> "我看到 KOL 喊一个币,准备买 $200,系统提示'此 token 卖出失败率 95%(疑似蜜罐)',我感谢系统救我命。"

### US6.2 — 黑名单地址
> "我转账时输错了地址,系统识别为 OFAC 制裁名单 → 拒绝交易 + 提醒'此地址在制裁清单'。"

### US6.3 — 高税率
> "某个 token 买卖各收 15% 税,我没注意。系统提示'此 token 总税率 30%,实际到手只有 70%' 让我重新决定。"

## 6.2 5 道筛(顺序执行)

### 筛 1 — 黑名单地址(Recipient / Token / Pool)

**类型**:
- OFAC 制裁名单(美国财政部公布)
- 已知诈骗地址(社区反馈 + 我们维护)
- 已被入侵 / 跑路的合约
- 蜜罐 / 老鼠仓 token(已知)

**数据源**:
- Chainalysis API(主要,付费)
- Etherscan/Solscan 公开标签
- 我们自己维护的"用户反馈过的诈骗地址"

**生效**:用户输入地址 / 选 token 时,实时查 → 命中拦截 + 红色警告。

### 筛 2 — 蜜罐检测(Honeypot)

**蜜罐定义**:某 token 能买不能卖,合约里藏代码限制特定地址 / 时间。

**检测方法**:
- 模拟卖出(eth_call simulating sell)→ 失败 = 高度怀疑
- 历史卖单成功率 < 50% = 怀疑
- 合约源码扫描"transfer 限制" = 怀疑

**生效**:用户准备买入前,后端 30 秒预检 → 命中蜜罐 → modal 拦"此 token 疑似蜜罐,卖出失败率 X%,确认仍买?" 用户必须二次确认才能继续。

### 筛 3 — 高税率(Buy Tax / Sell Tax)

**典型场景**:某些 meme 币合约里有 5%-15% 买卖税,用户不知道。

**检测**:
- 模拟买卖 → 实际到手 vs 应到手的差 = 税率
- 总税(买税 + 卖税)> 10% → 警告
- 总税 > 30% → 强制拦截

**生效**:报价时显示"总税 X%,你将损失 Y" → 高税强提示。

### 筛 4 — 极低流动性

**判定**:Token 总流动性 < 用户金额 × 5(用户 $200 但池子 $800,买完会冲高 25%)

**生效**:报价时警告"流动性偏低,建议拆单 or 减小金额"。<$5k 流动性强烈警告。

### 筛 5 — 集中度过高

**判定**:Token top10 持仓 > 70%(单一钱包/团队控盘明显)

**生效**:警告 "集中度高,rug 风险" + 显示 top 1 持仓占比。

## 6.3 拦截级别

| 级别 | 用户感知 | 能否绕过 |
|---|---|---|
| **强阻断**(REJECT)| 红色弹窗,只能取消 | ❌ 不能绕过(OFAC / 已知跑路) |
| **强警告**(WARN_HARD)| 红色 modal "此 token 疑似 X,确认继续?" | ✅ 双重确认才能继续 |
| **弱警告**(WARN_SOFT)| 黄色 banner 显示风险 | ✅ 用户随意继续 |

## 6.4 阻断后的用户体验

### 6.4.1 透明告知

```
❌ 交易已拦截

原因:此 token 检测为蜜罐
依据:模拟卖出失败 + 历史卖单成功率 12%
建议:不要买入,选其他 token

[ 我了解,取消 ]    [ 仍要买入(慎选)]
```

强阻断时不显示"仍要买入"按钮。

### 6.4.2 风控历史可查

用户主页"风控保护记录":
```
最近 30 天为你拦截:
- 12 次蜜罐
- 3 次黑名单地址
- 5 次高税率提示

预估为你避免损失:$2,400
```

让用户感受到产品的"价值守护"。

## 6.5 风控规则更新

### 6.5.1 实时性要求

- 黑名单(OFAC)更新:每天 1 次拉取
- 蜜罐数据库:每小时更新一次新报告
- 用户反馈"此地址是诈骗" → 4 小时内 community review → 加入黑名单

### 6.5.2 误报机制

如果某 token 被错误标蜜罐 → 用户可投诉 → 我们 24 小时内核实 → 错的删除标记。

## 6.6 验收标准

| 标准 | 通过条件 |
|---|---|
| 黑名单拦截率 | 100%(OFAC / 跑路合约必拦) |
| 蜜罐检测准确率 | ≥ 95%(误报 < 3%,漏报 < 2%) |
| 用户感知 | 拦截原因清晰,90% 用户认同 "拦得对" |
| 性能 | 5 道筛总耗时 < 1 秒 |
| 实时性 | 黑名单更新到生效 < 4 小时 |

# §7 AI Agent 怎么帮人下单(差异化卖点)

> 一句话:**前面 6 个模块是工具底座,这一节定义"AI 怎么用这些工具帮人做决策"**。

## 7.1 用户故事(决定产品形态)

### US7.1 — 自然语言下单
> "我说'用 $300 跟 V神最近买的那个币',Agent 直接出 → 找到 V神 24h 内最大买入的 token → 检查蜜罐 / 流动性 / 风控 → 给我 1 行确认信息 → 我点确认就完成。"

### US7.2 — 决策辅助
> "我看到 $X 信号,但拿不准要不要跟。让 Agent 给我 3 行分析:'技术面 / 链上 / 情绪',我自己定。"

### US7.3 — 解释能力
> "Agent 帮我下单完了,我问'为什么选这个路径',Agent 应该说'因为 Jupiter 比 Raydium 便宜 0.3%,1.5 秒内出报价,蜜罐检查通过'。"

### US7.4 — 自主路由 vs 用户指定
> "默认 Agent 自己决定路由,但 Pro 用户可说 '强制走 Uniswap V3 不要 1inch',Agent 听话执行。"

### US7.5 — 失败回退
> "Agent 自动跟单失败 3 次,自动停 + 告诉我'已停跟单,3 次失败原因 X',让我决定下一步。"

## 7.2 AI 下单的 4 种交互模式

### 7.2.1 模式 A — 全自动(Fully Auto)

**适用**:用户已配置策略,Agent 检测信号自动执行。

**流程**:
```
1. 信号触发(鲸鱼买 / 聪明钱共识 / 用户策略命中)
2. Agent 走风控 5 道筛
3. Agent 选最优路由
4. 自动签名 + 提交
5. 推送结果"已跟单 X,均价 Y,目前余额 Z"
```

**用户参与点**:0(完全自动)

**风险**:必须有 daily cap + 余额 gate + 用户授权才开此模式。

### 7.2.2 模式 B — AI 建议 + 用户确认(默认推荐)

**适用**:大多数用户首次接触 Agent。

**流程**:
```
1. 信号触发
2. Agent 给建议:"这是 X 信号,推荐买 $Y,因为...,风险:...,你看?"
3. 用户点 [跟] / [改金额] / [跳过]
4. 点确认后,Agent 自动完成执行
```

**用户参与点**:1(看建议 + 点确认)

### 7.2.3 模式 C — 用户主动 + AI 优化

**适用**:用户已有交易决心,想 AI 帮选最佳路径。

**流程**:
```
1. 用户说 "买 $300 X 币"
2. Agent 走风控 + 路由(选最便宜路径 / 防夹 / 拆单)
3. 报价页显示 "最佳路径 + 节省 $5",用户点确认
4. 执行
```

**用户参与点**:2(发起 + 确认)

### 7.2.4 模式 D — 教练模式(V2)

**适用**:新手学习。

**流程**:
```
用户说"我想了解为什么大家买这个币"
Agent 分析 → 输出 "因为 X / Y / Z,但风险 A / B"
不下单,只解释
```

## 7.3 AI 决策的核心算法(产品视角)

### 7.3.1 决策树(每笔下单 AI 都跑这个)

```
1. 用户意图识别
   "买 $X 币"  → 直接路由
   "跟单 V神"  → 找 V神最近交易
   "我想做 SOL 上的事" → 进策略 / 推荐

2. 风控前置
   黑名单 / 蜜罐 / 高税 / 低流动 / 集中度
   → 任一命中 → 拒绝 + 告诉用户原因

3. 路径规划
   选 DEX / 拆单决策 / 滑点推荐 / MEV 防护

4. 大小判断
   $X < $500 → 直接执行
   $500 ≤ $X ≤ $5000 → 一秒预览给用户看
   $X > $5000 → 二次确认 + 解释

5. 执行 + 监控
   提交链上 / 重试逻辑 / 失败回滚
```

### 7.3.2 解释能力

**每个决策都必须能解释**。Agent 内部记录:
- 选这个 DEX 的原因(便宜 / 快 / 防夹)
- 这个滑点的依据(token 流动性 / 历史波动)
- 这个时机的判断(信号强度 / 风险评分)

用户问"为什么"时,系统能 1 秒返回:
```
"我选 Jupiter 因为它比 Raydium 便宜 $0.30。
 滑点设 0.8% 因为这个 token 24h 波动稳定。
 现在执行因为信号 1 分钟前刚出且未被多人跟单。"
```

## 7.4 AI 不该越权的场景

| 场景 | AI 行为 |
|---|---|
| 用户余额 < 10% 总值 | 拒绝执行,提示用户 |
| 单日交易 > 设定上限 | 拒绝 |
| 大额(>$5k)用户首次跟单某鲸鱼 | 必须用户确认,不全自动 |
| 蜜罐 / 高风险 token | 拒绝,无法绕过 |
| 系统自身故障(数据延迟>1分钟)| 暂停 Agent,通知用户 |

## 7.5 AI 失败回退

### 7.5.1 单笔失败

```
Agent 自动跟单 3 次连续失败
  → 自动暂停此 token 的跟单 1 小时
  → 通知"已暂停 X 跟单,失败原因 Y,1 小时后自动恢复"
```

### 7.5.2 系统级失败

```
- 数据源延迟 > 60 秒 → Agent 暂停所有自动决策,降级到"AI 建议 + 用户确认"
- 路由失败率 > 10%(过去 1 小时)→ 系统级告警 + 部分功能降级
- 余额耗尽 → Agent 拒接新指令,提示充值
```

## 7.6 AI 的 Action Log(可追溯)

每笔 AI 触发的交易必须可追溯:
- 触发原因(哪个信号 / 哪个策略命中)

- 链上 tx hash
- 用户最终视角看到的结果

用户在自己主页"我的交易"可看到完整轨迹:
```
2026-05-08 10:23  鲸鱼跟单 V神
  ↓ 信号:V神 10:22 买入 WBTC $80k
  ↓ 风控:全过(无蜜罐 / 无黑名单 / 流动性充足)
  ↓ 路径:Jupiter(SOL → WBTC,1 跳)
  ↓ 执行:0xABC...123,均价 $67,500
  ↓ 结果:你买入 $200 = 0.00296 WBTC
  ↓ 当前持仓价值:$201.20(+$1.20)
```

## A.3 关键决策树伪代码(给后端参考思路)

### A.3.1 路由选择决策树

```
input: quote_options[], user_preference

1. 滤掉过期报价(quote_expires_at < now)
2. 滤掉风控不通过的 DEX(蜜罐 / 黑名单)
3. 按 user_preference 排序:
   - fast      → 最快确认
   - best_price → out_amount 最大
   - private   → MEV 防护强的
4. 选 top 1
5. 如果 out_amount 比次优低 < 0.1% → 选第二便宜的(避免单点依赖)
```

### A.3.2 拆单决策树

```
input: amount_usd, token_liquidity, token_24h_volume

if amount_usd > 5000 OR
   amount_usd > token_liquidity * 0.1 OR
   amount_usd > token_24h_volume * 0.1:
   → split = True
   split_count = ceil(amount_usd / 1000)  # 每笔约 $1000
   split_interval = 5 + random(0, 25) seconds  # 5-30 秒错峰
else:
   → split = False
```

### A.3.3 滑点动态推荐

```
input: token_meta, regime

base_slippage =
  major_token: 0.5%
  liquidity > 1M: 1%
  liquidity > 100k: 2%
  liquidity > 10k: 3%
  else: 5%

multiplier =
  regime == CRISIS: 1.5
  token_24h_volatility > 50%: 1.3
  else: 1.0

final_slippage = base_slippage × multiplier
return min(final_slippage, 10%)  # 最大不超过 10%
```
